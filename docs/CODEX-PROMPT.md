# Codex implementation prompt

Build **Little Joys**, the small touchscreen toybox specified in this folder. Produce a runnable implementation, not another plan or a static mock-up.

Read `README.md`, `SPEC.md`, `TASKS-AND-ACCEPTANCE.md`, `ASSETS.md`, and `RESEARCH.md` before implementing; use `SOURCES.md` when checking a technical or evidence claim. `SPEC.md` is normative. Work in a new project/repository; do not modify `MachineKomi/maze-so-puzzle`.

Use Vite, TypeScript, React for the semantic DOM shell, and an imperative Canvas2D runtime for the toys. Keep pointer movement and animation outside React render state. No server, runtime AI, accounts, tracking, large engine, curriculum, or progression system.

First build the complete end-to-end Squishy Friend slice with reliable multi-touch, genuine local deformation, pause, silent default, and responsive layout. Then implement Bubble Pond and Roll & Nest, the shared parent settings, optional bounded audio, original art, verified offline installation/update behaviour, and the required tests. A one-toy preview is not the complete MVP. Do not substitute whole-image scaling for the squish mechanic.

Use available OpenAI image-generation tooling during development for the limited art brief. Check actual model access and current official API/tool capabilities instead of inventing an endpoint or model identifier. Keep interactive geometry procedural. Reuse only selected owner-authorised assets from the existing maze repository after checking their provenance and visual suitability. Do not copy the whole asset archive or Nintendo/Super Simple assets. Never put a generation API key in the client. If generation is unavailable, finish a usable procedural-art build and report the limitation accurately.

Follow the staged tasks and requirement IDs. Add and run unit, browser, asset-budget, and production-build checks. Have an independent reviewer inspect interaction, screenshots, code, and evidence; address concrete defects for up to four review/repair rounds. Do not claim observed child enjoyment or educational efficacy. Do not count desktop WebKit as a physical iPad test.

Keep all child/family names, diagnoses, transcripts, photos, and private playtest notes out of public source, prompts, telemetry, and runtime assets. The child never has to speak, make eye contact, answer correctly, or take a turn to continue playing. Honour all stop/pause paths. Preserve silent play and reduced-motion behaviour.

Prepare a static Vercel deployment from `dist`. If the current environment has authorised deployment access to this new project, deploy a preview, open the actual URL, and verify it. Otherwise deliver a complete deployable repository and exact deployment instructions without inventing a URL or claiming to have deployed. Do not create a paid service, purchase a domain, modify the existing game, or silently make private source public.

Finish with the runnable project, setup/build/test commands, actual test results, requirement coverage, asset provenance, measured budgets, deployment status, known issues, and the exact physical-iPad checks still pending. Continue implementing against the spec rather than expanding the scope or returning a speculative roadmap.
